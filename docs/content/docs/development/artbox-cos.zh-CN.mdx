# ArtBox 与腾讯云 COS 配置

画布调用 ArtBox 时，浏览器只向项目后端提交 `assetId`。后端从私有腾讯云 COS 为素材生成短时签名 URL，再使用服务端 ArtBox Key 请求 `/v1/video/generations`。`blob:` URL、`localhost` 地址和本地文件路径不会发给 Provider。

<Callout type="warn">
所有 COS 和 ArtBox 变量都只能注入 Fastify API 进程。不要把 Key 写入 `VITE_*`、浏览器配置、画布快照、Nginx 配置或 Git。
</Callout>

## 1. 服务端环境变量

先配置 `.env.example` 中现有的 PostgreSQL、身份与 SMTP 变量，再将下面两个变量块完整注入 API 进程。COS 块五项、ArtBox 块七项均为“全部配置或全部不配置”；只填一部分时，API 会在监听端口前拒绝启动。

### 腾讯云 COS

| 变量 | 规则 |
| --- | --- |
| `COS_SECRET_ID` | API 服务账号的 Secret ID |
| `COS_SECRET_KEY` | API 服务账号的 Secret Key |
| `COS_BUCKET` | COS 的 `bucket-appid` 全名，例如 `canvas-assets-1250000000` |
| `COS_REGION` | 纯地域名，例如 `ap-guangzhou`；不填域名或 URL |
| `COS_SIGNED_URL_TTL_SECONDS` | 签名上传、预览和 Provider 取回素材的有效秒数，必须显式填正整数 |

### ArtBox

| 变量 | 规则 |
| --- | --- |
| `ARTBOX_BASE_URL` | 由供应商确认的 HTTPS API origin；不带 `/v1`、路径、查询、用户名或密码，不能根据控制台网址猜测 |
| `ARTBOX_API_KEY` | 在 [ArtBox 控制台](https://artbox.top/dashboard/overview) 获取的服务端 Key |
| `ARTBOX_VIDEO_MODELS` | 英文逗号分隔的允许列表；当前画布模型为 `Artdance 2 Mini-480p` |
| `ARTBOX_REQUEST_TIMEOUT_MS` | ArtBox 创建、查询和结果下载单次请求的超时毫秒数，必须显式填正整数 |
| `ARTBOX_RESULT_MAX_BYTES` | 允许写入 COS 的单个结果最大字节数，必须显式填正整数 |
| `ARTBOX_RESULT_ALLOWED_HOSTS` | ArtBox 结果 URL 的精确 hostname 允许列表，英文逗号分隔；不带 scheme、端口、路径或通配符 |
| `ARTBOX_POLL_LEASE_SECONDS` | 同一生成任务的查询租约秒数，必须显式填正整数 |

这四个时间/大小边界在源码中故意没有默认值。请根据实际 ArtBox 响应时间、模型结果上限和并发策略选值，不要直接照抄测试值。`COS_SIGNED_URL_TTL_SECONDS` 还必须覆盖 Provider 实际拉取输入素材的时间。

生产环境的 `ARTBOX_BASE_URL` 和结果 URL 都必须是 HTTPS。如果供应商只给出 HTTP IP，应先为它配置可验证的 HTTPS 网关/域名，不要让浏览器直连。接口字段可对照 [New API 文档](https://docs.newapi.pro/zh)，但画布不接受用户自定义 Provider 字段。

## 2. COS 存储桶与 CORS

1. 将 Bucket 设为私有读写，不要配置公网匿名读。上传、预览和 Provider 读取均依赖短时签名 URL。
2. ArtBox 结果 Bucket 必须从未开启版本控制；不要对已开启或曾暂停版本控制的 Bucket 部署此结果写入路径。服务端依据[腾讯 COS PUT Object 官方说明](https://cloud.tencent.com/document/product/436/7749)，使用 `x-cos-forbid-overwrite: true` 原子创建结果对象：同名对象已存在时 COS 返回 `409 FileAlreadyExists`，服务端只 HEAD 校验并复用首个对象，不会覆盖。`If-None-Match: *` 仅作为额外防护，不是这一不变量的依据。若现有 Bucket 不满足条件，请新建从未启用版本控制的私有 Bucket 并迁移后再启用 ArtBox。
3. 给 API 服务账号授予 `assets/staging/` 和 `assets/final/` 前缀下所需的最小读取、写入、HEAD/校验、复制和删除 staging 权限；不要使用 Bucket 管理员长期 Key。
4. 在 COS CORS 中分别列出真实 Web origin，例如生产 `https://canvas.example.com` 和本地 `http://localhost:3000`。不要使用 `*`。
5. 允许 `PUT`、`GET`、`HEAD`，允许请求头 `Content-Type`。当创建 Asset 接口返回其他必需签名请求头时，再精确加入那些头。当前上传使用 `credentials: omit`，无需开放 CORS 凭证。

`ARTBOX_RESULT_ALLOWED_HOSTS` 填的是 ArtBox 任务完成后返回的视频 URL hostname，不一定是 `ARTBOX_BASE_URL` 的 hostname。先用供应商提供的真实结果确认 CDN hostname，再将其精确加入允许列表。

## 3. 本地与生产保持同一请求边界

本地开发使用：

```text
Web: http://localhost:3000
API: http://127.0.0.1:4000
Browser request: http://localhost:3000/api/...
```

`web/vite.config.ts` 已将 `/api` 反向代理到 `127.0.0.1:4000`。本地设置 `APP_ORIGIN=http://localhost:3000`，并在 COS CORS 中加入该 origin。完成数据库迁移后，分别运行：

```bash
bun --cwd server run db:migrate
bun run dev:api
bun run dev:web
```

生产使用 `NODE_ENV=production`、HTTPS `APP_ORIGIN` 和同源 Nginx `/api` 反向代理。反向代理规则要放在 SPA 的 `location /` 之前：

```nginx
location /api/ {
    proxy_pass http://127.0.0.1:4000;
    proxy_http_version 1.1;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
}

location / {
    try_files $uri $uri/ /index.html;
}
```

Nginx 与 API 的请求超时不得短于部署选定的 `ARTBOX_REQUEST_TIMEOUT_MS`。不要把前端改为请求 API 的独立域名；保持 `/api/auth` 和 `/api/v1` 与 Web 同源，才能与本地 Vite 代理共用同一套画布代码和会话 Cookie。

<Callout type="warn">
上述 Nginx 片段是外部部署前置条件，不是对仓库现有 `nginx.conf` 的描述。根 `Dockerfile`、Vercel 和 Render 配置目前只覆盖静态前端，不会启动 Fastify API、执行 PostgreSQL 迁移或提供 `/api` 反向代理；仓库也没有现成的生产 API build/start 与进程编排。生产发布需要将本功能与承载 API/PostgreSQL/Nginx 的部署分支集成；当前候选是 `origin/codex/tencent-deploy`，并需在其 `api` service 注入上述 COS/ArtBox 变量。该集成与线上冒烟尚未在本 worktree 完成，请不要将本功能分支单独当作已验证的生产部署方案。
</Callout>

## 4. 不暴露 Key 的冒烟检查

先通过应用的正常登录流程获得 Netscape 格式的 Cookie jar，保存在仓库外并设为仅当前用户可读。下列请求不传递、不打印 ArtBox 或 COS Key：

```bash
export CANVAS_ORIGIN=https://canvas.example.com
export WORKSPACE_ID=replace-with-workspace-uuid
export ASSET_ID=replace-with-existing-ready-asset-uuid
export SESSION_COOKIE_FILE=/secure/path/canvas-session.cookies

curl --fail --silent --show-error \
  "$CANVAS_ORIGIN/api/v1/health/live"

curl --fail --silent --show-error --output /dev/null \
  --write-out 'asset read HTTP %{http_code}\n' \
  --cookie "$SESSION_COOKIE_FILE" \
  "$CANVAS_ORIGIN/api/v1/workspaces/$WORKSPACE_ID/assets/$ASSET_ID"
```

第二个请求应输出 `asset read HTTP 200`，但不会把响应中的短时签名 URL 打印到终端。还可以用一个不存在的合法任务 ID 验证 ArtBox 路由与配置，该检查不会发起 Provider 生成：

```bash
ARTBOX_PROBE_ID=00000000-0000-4000-8000-000000000000
status=$(curl --silent --show-error --output /dev/null --write-out '%{http_code}' \
  --request POST \
  --cookie "$SESSION_COOKIE_FILE" \
  "$CANVAS_ORIGIN/api/v1/workspaces/$WORKSPACE_ID/integrations/artbox/video-generations/$ARTBOX_PROBE_ID/poll")
test "$status" = 404 && echo 'ArtBox route/config/session OK'
```

在会话有效、账号属于该 Workspace 且 COS/ArtBox 块完整时，预期为 `404`（随机任务不存在）。`401` 表示会话问题，`403/404` 也可能是 Workspace 归属不正确，`503` 表示 COS 或 ArtBox 配置块未完整注入。
