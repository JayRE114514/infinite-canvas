# Canvas Data Structure

## Storage

Authenticated Canvas lists, titles, snapshots, and revisions are server-authoritative through the Workspace Canvas API and PostgreSQL. The browser keeps two separate local domains:

- `infinite-canvas-recovery`, native IndexedDB version 1, stores per-session recovery drafts plus epochs and conflict markers. It is not the Canvas authority.
- `infinite-canvas`, managed through localForage, stores My Assets and other application state in `app_state`; image blobs use `image_files`, and other media blobs use `media_files` until the Asset cutover.

The cloud snapshot never persists session-scoped `blob:` URLs. During the media transition it may retain stable `storageKey` metadata, while the actual byte is still local and therefore unavailable on another device until it becomes an Asset.

## Project

```ts
type CanvasProject = {
  id: string;
  title: string;
  createdAt: string;
  updatedAt: string;
  nodes: CanvasNodeData[];
  connections: CanvasConnection[];
  chatSessions: CanvasAssistantSession[];
  activeChatId: string | null;
  backgroundMode: "lines" | "dots" | "blank";
  viewport: { x: number; y: number; k: number };
};
```

The in-memory project exposes a viewport for rendering, but viewport persistence belongs only to `recovery.envelope.localUi`. The canonical cloud snapshot uses a stable document viewport and pan/zoom alone does not advance the cloud revision.

## Nodes and edges

```ts
type CanvasNodeData = {
  id: string;
  type: "image" | "text" | "config" | "video";
  title: string;
  position: { x: number; y: number };
  width: number;
  height: number;
  metadata?: CanvasNodeMetadata;
};

type CanvasConnection = {
  id: string;
  fromNodeId: string;
  toNodeId: string;
};
```

Canvas IDs are generated by the server. Node positions and sizes use canvas-world coordinates. Edges store only node IDs; their paths are calculated while rendering. Deleting a node removes its connected edges.

Common metadata includes content, prompt, status, generation mode, model, size, count, natural dimensions, image results, input order, `storageKey`, MIME type, and byte size. A multi-image generation remains one image node: `images` creates all requested slots before generation starts and records each slot's `status`, `errorDetails`, and completed image data. `primaryImageId` selects the result mirrored by the node-level `content` and image metadata; the first successful slot becomes primary immediately. Persisted image and video `content` values are normally session-scoped `blob:` URLs, with `storageKey` as the persistent identity. If CORS prevents reading an otherwise displayable image, `content` may remain a potentially expiring remote URL and `storageKey` is omitted.

## Assistant sessions

```ts
type CanvasAssistantSession = {
  id: string;
  title: string;
  messages: CanvasAssistantMessage[];
  createdAt: string;
  updatedAt: string;
};
```

Message references and generated images use the same blob-storage rules. They are converted to data URLs temporarily only when an AI endpoint requires base64.

## Media lifecycle

`uploadImage()` accepts a Blob, data URL, or remote URL. It downloads remote data once, verifies that the Blob decodes as an image, stores it in `image_files` under an `image:<id>` key, and returns an in-memory object URL plus metadata. If CORS blocks byte access but the browser can still display the remote image, it returns that URL without a storage key. Opening a project resolves each stored key into a fresh object URL.

Cleanup uses explicit release semantics. When nodes, assets, or assistant content are removed, the caller supplies the data being released. The application compares those keys with the active canvas, undo history, and My Assets, then deletes only released keys that are no longer retained. It never scans the local blob stores and treats files absent from the current page as garbage, because other server-backed canvases may still reference them. Confirmed deletions also revoke object URLs and remove them from the in-memory cache.
