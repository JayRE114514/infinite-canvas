# Pending Tests

The current release needs manual verification in these areas:

- Backend Workspace credits: an active platform administrator can grant a positive canonical decimal amount through `POST /api/v1/admin/workspaces/:workspaceId/credits/grant` with an explicit idempotency key; amounts above JavaScript's safe integer range must round-trip exactly. Repeating the same key and body must return the original transaction and unchanged balance, while the same key with a different body returns `idempotency_conflict`. An active Workspace member can read only that Workspace's available/held balance through `/api/v1/workspaces/:workspaceId/credits/balance`. Each successful admin attempt must have one immutable xid-bound audit, while the ledger keeps one balanced immutable transaction and Wallet projection for an idempotent grant.
- Platform-credit image Task remaining failure paths: the local SeaweedFS S3-compatible and real Wawapi Gemini native happy path has been manually verified through `202 queued`, a single persistent SSE connection, `ready` Asset storage, exact reserve/capture accounting, same/different idempotency-key behavior, same-origin content headers/Digest, and browser display without a Provider URL fallback. Still verify startup refusal and secret redaction for every missing or invalid deployment setting; content-stream cancellation plus stable 404/409/503 behavior without Task/Hold/ledger mutation; ambiguous Provider results retaining the active Hold in `reconciling`; and Worker crash/restart across lease expiry without duplicate submit or settlement. Remote production S3 and the OpenAI-compatible `/images/generations` Adapter remain manually unverified.
- Documentation navigation and page contents: at phone width, opening the documentation sidebar should show the current section and its description at the top. Expanding it should allow switching among Overview, Canvas Guide, Development, Progress, Business, and Support; the selected section and page list should update together while the desktop top tabs remain unchanged. At widths of 960px and above, a table of contents with hierarchical track lines should appear to the right of the article, support heading navigation, and highlight the current heading while scrolling; narrower layouts should keep the top collapsible contents control.

- Backend database roles and least privilege (see the [Gate 0 Backend Verification Record](/docs/progress/gate-0-backend-verification)): `schema_owner`, `app_api`, `app_worker`, and `app_maintenance` must be four separate login roles, all `NOSUPERUSER NOBYPASSRLS`, with no runtime role owning business objects and only `schema_owner` running migrations. The API process must connect only as `app_api` and must refuse readiness — rather than degrade — when the effective role, object ownership, or BYPASSRLS attribute does not match. The grant matrix must hold item by item: `app_api` may update only `name`, `slug`, `status`, `deleted_at`, and `updated_at` on `workspaces`, only `title`, `snapshot_json`, `revision`, `updated_by`, `updated_at`, and `deleted_at` on `canvases`, and may only INSERT into `workspace_audit_logs`; `app_maintenance` may read only `id` and `status` on `workspaces`; `app_worker` has no canvas privilege at all. Statements outside that matrix — hard-deleting a canvas, rewriting `workspace_id`, rewriting `document_mode`, or rewriting the deletion-receipt column — must fail with `42501` instead of silently succeeding or returning an empty result.
- Backend transaction-scoped tenant context and RLS: tenant context must use only transaction-local `set_config(..., true)` that expires on commit or rollback, leaving no `app.user_id` or `app.workspace_id` on a connection returned to the pool. Membership verification and business SQL for one request must run on the same transaction and connection. - Backend personal Workspace provisioning and explicit repair: the email-verification callback must create exactly one personal Workspace and write one `email_verification` provisioning audit. When that callback fails or was never delivered, `POST /api/v1/workspaces/personal/repair` must converge on the same personal Workspace through `explicit_repair`, replay idempotently by event ID with the same result and no extra audit row, and reject any request body with `invalid_request_body`. - Backend Workspace lifecycle and administrator audit: the platform-admin `GET /api/v1/admin/workspaces/:workspaceId` and the `suspend`/`deactivate`/`restore` actions must run through the narrow `SECURITY DEFINER` function inside one transaction. Only active → suspended, active or suspended → deactivated, and suspended or deactivated → active are allowed; other combinations return a stable error and a concurrent status change returns `workspace_status_transition_conflict`. Every read and every transition must write exactly one immutable audit row carrying `operation_id` and the transaction xid, and a non-administrator caller must receive `platform_admin_forbidden`. Owner self-service deactivation must still be limited to active → deactivated and must write its audit before the status update in the same transaction.
- Backend cloud-canvas snapshot document mode: `documentMode` must always be `snapshot` on create and read, and neither the create nor the save body may accept that field — sending it must fail as an unknown field with `invalid_request`. Save must keep a fixed decision order: an invisible or soft-deleted row returns 404 `canvas_not_found`, a non-`snapshot` mode returns 409 `canvas_document_mode_mismatch`, a stale revision returns 409 `revision_conflict`, and `canvas_revision_limit_reached` appears only when the stored revision and `baseRevision` are both 9007199254740991. If the conditional update still returns zero rows after every locked check passed, the request must roll back and return the sanitized non-retryable 500 `canvas_save_invariant_failed` while the server log records `requestId`, `canvasId`, `workspaceId`, and the expected revision.
- Backend cloud-canvas deletion receipt: deletion is an idempotent state transition. The first DELETE has the database trigger issue `deletionReceipt`, and replaying the same deletion must return that receipt byte-for-byte with no second state change; a broken invariant must surface as the sanitized non-retryable 500 `canvas_delete_invariant_failed`. Ordinary GET and list 404 responses must never carry a receipt, and cross-Workspace, removed-member, suspended, or deactivated-Workspace deletions must never obtain one. The database must reject forgery: inserting an already-deleted state directly, rewriting an issued receipt, shifting `deleted_at`, and clearing the deletion pair to resurrect a canvas must all fail, and an active row must never spontaneously carry a receipt.

- Local storage settings: the Settings page should provide a Local storage tab that reads only the `infinite-canvas` database and shows IndexedDB usage, total site usage, browser quota, quota percentage, and per-object-store record counts and content size; refreshing after local data changes should update the figures without blocking the rest of the page.
- Cloud canvas schema and contracts: the `0001_canvases` migration should apply cleanly on top of `0000_auth_and_workspaces` and create a `canvases` table with a database-generated UUID primary key, a JSONB snapshot column, a `revision` counter defaulting to 0, soft-delete `deleted_at`, and a `(workspace_id, updated_at DESC)` index. No foreign key may delete shared canvas data: deleting an ordinary member account should only clear the nullable `created_by` and `updated_by` attribution to null and leave the canvas readable by other members, while physically deleting a workspace row should be refused so removal stays on the soft lifecycle. Note that deleting the account that owns a workspace may still be blocked entirely today, because workspace ownership cascades from the account while canvases restrict workspace deletion; unblocking it needs an ownership-transfer or workspace-deletion lifecycle that does not exist yet. Database CHECK constraints should reject a `revision` below zero or above 9007199254740991. Canvas contract validation should reject empty or over-length titles, non-integer, negative, or above-safe-integer `baseRevision` values, unknown request and response fields, and snapshot values that are not valid JSON such as `bigint`, `undefined`, functions, `Symbol`, `NaN`, or `Infinity` at any nesting depth, including under keys containing newline, carriage return, U+2028, or U+2029 while those line-break keys still accept valid JSON values; canvas summaries should omit the snapshot payload, and a save may carry an optional bounded `title` alongside the required snapshot.
- Cloud canvas API: create a Canvas without a snapshot and confirm it returns `{ canvas }` with `{}` and revision 0; list it through `{ canvases }` without any snapshot field, then load, rename, save, and soft-delete it. A matching save must update title and snapshot together and increment revision once; a stale save must return `revision_conflict` without overwriting either value, and a max-safe `baseRevision` must be classified by the stored revision: `canvas_revision_limit_reached` only when the stored revision is also 9007199254740991, `revision_conflict` when the live row sits at a lower revision, and `canvas_not_found` when the row is missing or soft-deleted, all without overflow. Verify LF, CR, U+2028, and U+2029 JSON keys round-trip through both create and save, while unknown fields and malformed non-JSON values return `invalid_request`. Create and save bodies over 10 MiB must return the stable `canvas_snapshot_too_large` error while unrelated routes keep Fastify's 1 MiB default. Canvases seeded in two Workspaces must each list only their own IDs, a member of another Workspace must see the same `canvas_not_found` result as a missing ID, and a save to a missing ID must leave sibling canvases byte-identical. Saving an already soft-deleted Canvas must return 404 without changing its snapshot, title, or revision. Under concurrency, two same-base saves must yield exactly one success and one `revision_conflict` with the stored row equal to the winner, two authorized deletes must both succeed with one deleted state, and a simultaneous save and delete must end in one of the valid linearized states with no resurrection or partially applied write.
