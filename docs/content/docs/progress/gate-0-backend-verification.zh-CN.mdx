## 数据库角色与最小权限

`server/database/bootstrap/roles.sql` 幂等创建四个固定登录角色，并反复重申属性：`LOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE NOINHERIT NOBYPASSRLS`。`schema_owner` 只用于发布期迁移作业，三个运行期角色都不拥有业务对象。进程启动时由 `server/src/infrastructure/database/role-assertions.ts` 校验实际生效角色、对象归属与 BYPASSRLS 属性，不符即拒绝就绪。

`0004_tenant-rls.sql` 先从 `PUBLIC` 和三个运行期角色收回全部表、序列、函数权限与 `CREATE ON SCHEMA public`，再逐项授予：

| 对象 | app_api | app_worker | app_maintenance |

| `users` / `sessions` / `accounts` / `verifications` | SELECT, INSERT, UPDATE, DELETE | 无 | 无 |
| `workspaces` | SELECT, INSERT, UPDATE(`name`, `slug`, `status`, `deleted_at`, `updated_at`) | 无 | SELECT(`id`, `status`) |

## 事务级上下文与行级安全

租户上下文只使用事务局部 `set_config(key, value, true)`，提交或回滚后自动失效，连接归还池中不残留任何应用变量。策略侧统一用 `nullif(current_setting('app.user_id', true), '')` 读取，缺失时为 NULL，策略求值为假，因此"没有上下文"的结果是 0 行而不是报错。

`server/src/infrastructure/database/transactions.ts` 是唯一的业务事务入口，共四个：`withUserTransaction`、`withTenantTransaction`、`withWorkerTransaction`、`withPlatformAdminTransaction`。成员校验与业务 SQL 跑在同一个事务和同一条连接上。

启用范围：`workspaces`、`workspace_members`、`workspace_invitations`、`canvases`、`workspace_audit_logs` 全部 `ENABLE ROW LEVEL SECURITY`；其中 `workspace_invitations`、`canvases`、`workspace_audit_logs` 额外 `FORCE`，表属主也不能绕过。

| 表 | 关键策略 | 判定条件 |
| --- | --- | --- |
| `workspaces` | `workspaces_api_select_member` | 用户维度读取，不要求 Workspace 上下文，供 `GET /api/v1/workspaces` 使用 |
| `workspaces` | `workspaces_api_update_manager` / `workspaces_api_update_owner_deactivate` | 必须同时命中精确 Workspace 上下文与管理角色；所有者自助下线只允许 active → deactivated |
| `workspace_members` | `workspace_members_api_select_self` / `_select_workspace` / `_delete_manager` | 自读直接比较 `user_id` 不递归；成员列表与移除都要求精确上下文与管理角色，且不得移除 owner |
| `workspace_invitations` | `_select_manager` / `_select_recipient` / `_update_manager` / `_update_recipient` | 管理员只能 pending → canceled；接收人只能在未过期时 pending → accepted/rejected |
| `canvases` | `canvases_api_select_member` / `_insert_member` / `_update_member` | 必须同时命中精确 Workspace 上下文与活跃成员身份 |
| `workspace_audit_logs` | `_api_insert_owner` / `_schema_owner_insert_admin` | 只追加；管理员审计只能由 xid 绑定的窄口函数在同一事务内产生 |

画布 SELECT 策略刻意不把 `deleted_at` 作为谓词：软删除由服务层过滤，这样授权成员重放删除时仍能锁定已删除行并读回持久回执。

## Workspace 生命周期

平台管理员入口是 `GET /api/v1/admin/workspaces/:workspaceId` 与 `suspend` / `deactivate` / `restore` 三个动作，全部通过同一事务内的窄口 `SECURITY DEFINER` 函数 `execute_workspace_admin_operation()` 执行。

| 用途 | 允许的起始状态 | 目标状态 |
| --- | --- | --- |
| `workspace_read` | 任意 | 不变更状态 |
| `workspace_suspend` | active | suspended |
| `workspace_deactivate` | active、suspended | deactivated |
| `workspace_restore` | suspended、deactivated | active |
| 团队所有者自助下线 | active | deactivated |

非法流转由函数抛出 `P4091`，并发状态变更抛出 `P4092` 并映射为 `workspace_status_transition_conflict`，非管理员调用得到 `42501` 并映射为 `platform_admin_forbidden`。每次操作恰好写入一条带 `operation_id` 与 `pg_current_xact_id()` 的不可变审计，且审计写在最终状态更新之前。

## 个人 Workspace 供给与显式修复

供给来源固定为两个值：`email_verification`（邮箱验证回调）与 `explicit_repair`（显式修复）。两者都通过 `record_workspace_provisioning(source, workspace_id, event_id)` 写入不可变供给审计；该函数固定 `search_path`、要求事务局部 `app.user_id`，缺失时抛 `42501`，来源不在词表内抛 `22023`。

显式修复入口是 `POST /api/v1/workspaces/personal/repair`，事件 ID 由用户 ID 派生，因此重复调用按事件 ID 幂等收敛到同一个个人 Workspace，不会新增审计；该接口不接受请求体，带 body 返回 `invalid_request_body`。

## 画布 snapshot 模式、保存与删除回执

`0006_canvas_document_mode.sql` 新增 `document_mode`（默认 `snapshot`）与可空唯一的 `deletion_receipt_id`，并加上三个约束：`canvases_document_mode_check`、`canvases_deletion_state_check`（`deleted_at` 与回执必须同时为空或同时非空）、`canvases_deletion_receipt_unique`。回填只针对发布前已软删除的行，在同一迁移事务内临时 `NO FORCE` 后立即恢复 `FORCE`，条数不符即整体回滚。

`document_mode` 对客户端只读：`documentMode` 只出现在响应契约，创建与保存请求体都是 `additionalProperties: false` 且不含该字段。

保存的判定顺序在同一次行锁内固定为：

1. 行不可见、不存在或已软删除 → 404 `canvas_not_found`
2. 模式不是 `snapshot` → 409 `canvas_document_mode_mismatch`
3. `revision` 与 `baseRevision` 不一致 → 409 `revision_conflict`
4. 存储版本与 `baseRevision` 同为 9007199254740991 → 409 `canvas_revision_limit_reached`
5. 上述检查全部通过后条件更新仍为零行 → 回滚并返回脱敏、不可重试的 500 `canvas_save_invariant_failed`，同时记录 `requestId`、`canvasId`、`workspaceId` 与期望版本

删除回执由数据库触发器签发。`BEFORE INSERT OR UPDATE` 触发器覆盖三种情况：INSERT 阶段拒绝伪造删除状态；首次 active → deleted 跃迁强制由数据库生成回执并覆盖调用方自带值；回执签发后 `deleted_at` 与 `deletion_receipt_id` 逐字节不可变，改写、平移或清空（复活）都会失败。活跃行被直写回执时强制置 NULL。重放删除读取已持久化的回执，不产生第二次状态变更；普通 GET 与列表的 404 永远不包含回执。不变量被破坏时返回脱敏、不可重试的 500 `canvas_delete_invariant_failed`。

## 残余风险

- **浏览器范围**：原生 IndexedDB 事务/CAS 恢复、`web` typecheck/构建及 Chrome、Firefox 真实证据均已完成，详见 [Gate 0 前端验证记录](/zh-CN/docs/progress/gate-0-frontend-verification)。Safari 已明确豁免，状态是未验证而不是通过。
- **运行环境差异**：本地验证使用 Node v22.23.2，生产基线设想是 Node 24 LTS，发布前需要在目标版本复跑完整套件。
- **既有类型错误**：`server` 的严格 TypeScript 检查目前有 15 个报错（3 个在 `src/error-handler.ts`，12 个在测试与测试辅助代码），不在本计划范围内，尚未清理。
- **超级用户边界**：数据库超级用户仍可禁用触发器或改写复制角色以绕过删除回执不变量；四个运行期角色都没有该能力。
- **前端现状**：Web 端画布与"我的素材"仍以浏览器本地存储为主，AI API Key 也仍保存在浏览器并由前端直连上游，本页不代表已完成云同步或密钥托管。
- **未开始的后续 Gate**：积分钱包与账本、对象存储与素材生命周期、可靠 AI 任务队列、Provider Adapter 与 Yjs 实时协同都还没有实现。
- **部署未验证**：本页所有证据来自本地自动化测试，不包含生产部署、容量或故障演练结论。
